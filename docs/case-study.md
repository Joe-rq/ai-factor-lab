# Case study：一个陌生领域里，AI 研究系统是怎么被自己的错误教出来的

> **状态：第一稿。** 第 3 节的三起事故取自项目记忆与对话记录，已去掉字段名、阈值与
> 平台读数；第 1、2、4、6 节为代拟稿，发布前需作者逐段用自己的话改定。
> 尤其是「当时为什么看着对」——那是只有作者能确认的部分。

## 1. 起点

开始这个项目时，我对这个领域的理解只到「能读懂术语，但读不懂一个读数为什么可信」。
我知道语言模型可以批量生成表达式，也知道它能给每个结果编出一套解释；我不知道的是，
怎样把「结果好」和「结果只是看起来好」分开。这个项目要解决的就是这一件事。

## 2. 我决定造什么

不是造一个「能挖因子的 AI」，而是造一套**让 AI 的研究记录无法说谎**的装置：

- 候选有内容指纹，同一条候选不会因为换了条路径就变成两条；
- 账本里的结局是终态，重跑只能新增一次尝试，不能改写历史；
- 规则在跑之前冻结，跑完之后只能新增规则，不能假装旧规则一直是那样；
- 判读闸有三态：通过、失败、**根本没测到**——第三态不许被读成第二态。

这套东西不提高「挖到因子」的概率，它提高的是「知道自己什么时候在自欺」的概率。

## 3. 三起事故

### 事故一：闸判错了对象，而我给妥协编了个理由

**发生了什么。** 有一道闸，判据是「这个字段在过去有没有被证伪过」。账本按字段建索引，
只要该字段名下有任意一格被标成证伪，这个字段就整片报红。我拿着三张机制卡去开卡，
三张都用了同一个价格类输入作分母——闸全红。

我当时的处理是：把三张卡的分母全换成会计量，让闸变绿，然后继续跑。整批候选因此换了一个
形态，后续读数并不理想——而这次改动的起因，是闸判错了对象。

**当时为什么看着对。** 闸报红是机器给的确定信号，而我的设计改动看起来也「有道理」：
换成会计量之后，表达式不再带价格量纲，我甚至在卡里写了一句「无量纲性显出来了」。
那句话不是发现，是**事后合理化**——真实因果是闸红→改设计→编理由。

**后来查清了什么。** 闸的索引只按「被计算的字段」建，**分母那一侧根本不进索引**。
同一个输入，作被算字段时确实该封（有证伪格），作分母时却有大量成功记录——闸拿前者的
证伪去判后者的用法，判错了对象。

**系统改了什么。**
1. 判据从「字段下有任一格证伪就红」改成「有证伪格且**从未有过实测格**才红；两者都有则
   打出分格表交人自查」。
2. 加了一条硬纪律：**因装置而改设计，必须在卡里如实写「因闸红而改」**，不许记成「设计改进」。
3. 承认闸仍判不到「位置」那一层（卡侧不声明分子/分母），把它登记为限度，而不是假装覆盖了。

对应到本仓：`docs/positive-controls.md` 讲的是「闸会不会开火」；这起事故补的是另一半——
**闸开火了，但它判的是不是你以爲的那个量。**

### 事故二：三处一起改，主结论把功劳记错了人

**发生了什么。** 有一条腿，读数不错，但离过线还差一点。为了抬它，我一次改了三处：
换分母、加一层时序算子、换分组。改完读数大幅上升，我把主结论写成「**分母**带来了增益」。

**当时为什么看着对。** 三处里，分母是最「像机制」的那一处：它改变了表达式的归一化方式，
讲得通、也符合当时的先验。而且三处同改的那一发，读数确实是我想要的方向——**结果对了，
解释就被当成了因果**。

**后来怎么翻的。** 下一批把这条链拆成逐格只差一个变量的四次运行：
- 只换分母：sharpe 反而下降，returns 小幅变化；
- 在只换分母的基础上加时序算子：returns 跳升，换手同步暴涨；
- 换另一个分母：与第二格几乎逐位相同；
- 换分组：读数下降。

**归因被自己的单变量链推翻**：抬 returns 的主要是时序算子，分母只贡献零头。更糟的是，
那次三处同改的「成功」根本不是可归因的证据——它只是一条**探针**。

**系统改了什么。**
1. 一次只改一个变量；多处同改的运行**只能登记为探针，不能当对照腿**。
2. 归因结论必须由逐格单变量链支撑，且在跑之前写进预注册。
3. 报告里把「探针」与「对照」分开记——混在一起，下一次还会把探针当证据。

对应到本仓：`docs/preregistration.md` 的冻结规则，和 `docs/verification.md` 的判据层。

### 事故三：预注册自己和自己打架

**发生了什么。** 有一发候选，我给它写了两条预测：
- 一条是**绝对区间**：读数应落在某个范围；
- 另一条是**相对判据**：读数应低于前一条腿。

写的时候两条自洽，因为前一条腿的预测区间也在某个位置。但前一条腿实测落在了预测区间之外，
于是这一发无论怎么跑都不可能同时满足两条：要满足绝对区间就违反「低于前一条腿」，
要满足相对判据就违反绝对区间。**这一发的预测不可判**，作为 out-of-sample 证据的价值直接归零。

**当时为什么看着对。** 两条判据各自都合理，写下来时也彼此兼容。问题不在任何一条判据，
而在**参照系混用**：绝对区间锚在一个当时还没跑出来的实测值上，而它看起来像是个独立常数。

**系统改了什么。**
1. 一条判据只写一种参照系：要相对就全写相对（「前一条腿的 0.9–1.1 倍」），要绝对就只写绝对。
2. 链式对照里，后一条的绝对区间依赖前一条的实测值——前一条没跑完就不许写死绝对值。
3. 发现已经矛盾时，判读以相对判据为准，并把缺陷如实记进 findings；**不许事后改区间**。

对应到本仓：`prereg.py` 里每个闸都必须有 `not_measured` 槽位——不是为了好看，而是因为
「不可判」必须是一个**预先登记的合法结局**，不能等跑完再临时解释。

## 4. 人与 AI 的分工

| 决策 | 谁 |
|---|---|
| 什么问题值得问 | 人 |
| 测哪些假设与字段 | 人 |
| 起草预注册规则 | AI 出规则，人审阅放行 |
| 把假设展开成候选表达式 | AI |
| 跑流水线、落账 | AI |
| 判断结果值不值得行动 | 人 |
| 看到结果之后改闸 | 人，并留下书面理由 |
| 对外发布结果 | 人 |

这套分工的关键不是「AI 做什么、人做什么」的静态划分，而是**AI 不能自己晋升自己的产出**：
它可以起草规则、批量执行、给出第一读数，但规则要人放行，结果要人判断，发布要人按。

## 5. 成果

WorldQuant Challenge — Gold Level（2026）。官方证书，姓名已遮盖。

这个奖项是平台层面的认可，不构成对本仓库的背书。它证明的是「这套方法在一个真实平台上
拿到过结果」，不是「这套方法能保证结果」。

## 6. 给刚开始的人

1. 闸报红时，先核它判的是不是你以为的那个量，再改设计。因装置而改，就如实写「因闸红而改」，
   不要把它记成「设计改进」。
2. 一次只改一个变量。多处同改的运行只能当探针，不能当对照；因果结论必须由逐格单变量链支撑。
3. 写预测之前先选参照系。绝对与相对不许混用；「不可判」要在跑之前登记成合法结局，
   而不是跑完再解释。
